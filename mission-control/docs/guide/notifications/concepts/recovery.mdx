An alert tells your team that a resource became unhealthy. Recovery closes the loop: once the resource is healthy
again, Mission Control updates the same Slack thread or email conversation that carried the original alert.

Recovery is opt-in for each notification through `onResolved`.

## How it works

1. A health event fires and Mission Control delivers the notification as usual, applying `waitFor`, `filter`,
   silences, inhibitions and `repeatInterval`.
2. Mission Control records the delivery — the Slack channel and message timestamp, or the email recipients, sender
   and subject — and opens a health episode for the resource.
3. When the resource turns healthy, the episode ends. Mission Control waits for `onResolved.waitFor` of continuous
   health before acting, so a resource that flaps back to unhealthy does not produce a premature recovery.
4. Mission Control posts the recovery update to the recorded destination: a threaded Slack reply, a Slack reaction, or
   an email that replies to the original message.

Recovery works on the delivery, not on the trigger. A healthy event does not need to appear in `spec.events`, and the
original `filter`, silences, inhibitions and repeat limits are not applied a second time.

:::note What counts as healthy

Only a real transition to healthy resolves an outage. Unknown health, deletion of the resource, and a resource that
stops matching the notification's `filter` all leave the outage open.

A change between `warning` and `unhealthy` stays inside the same outage. A full healthy-to-unhealthy transition starts
a new outage, which gets a conversation of its own and resets repeat suppression.

:::

## Supported destinations

Recovery updates a destination that already received the original alert, so the transport must support a follow-up
message:

| Recipient | Supported |
| --------- | --------- |
| `to.connection` pointing at a Slack Connection | Threaded reply, emoji reaction, or both |
| `to.connection` pointing at an SMTP Connection | Reply to the original email |
| `to.email` or `to.person` over system SMTP | Reply to the original email |
| `to.team`, where the team rule selects one of the transports above | Same as the selected transport |
| `fallback`, when the fallback delivery is the one that succeeded | Same as the selected transport |

Grouped notifications, `to.playbook`, `to.webhook`, generic `slack://` URLs and every other Shoutrrr transport are
rejected when the notification is validated, and again when a send is dispatched.

:::info Supported events
`onResolved` accepts `config.healthy`, `config.warning`, `config.unhealthy`, `config.degraded`, the matching
`component.*` events, `check.passed` and `check.failed`. `groupBy` and `onResolved` cannot be combined.
:::

## Examples

### Reply in the Slack thread

This notification alerts on unhealthy Kubernetes deployments through a Slack Connection, and marks the recovery on the
same message.

```yaml title="recovery-slack.yaml" file=<rootDir>/modules/mission-control/fixtures/notifications/recovery-slack.yaml {27-32}
```

This example:

1. Uses `waitFor: 1m` to hold the initial alert until the deployment has been unhealthy for a minute.
2. Uses `onResolved.waitFor: 30s` to require 30 seconds of continuous health before the recovery update.
3. Uses `slack.reply` to post the update in the original thread and `slack.reaction` to add a
   `:white_check_mark:` to the original message.

Give `reaction` the emoji name on its own — `white_check_mark`, not `:white_check_mark:`. Set `reply`, `reaction`, or
both; a `slack` block that disables `reply` without a `reaction` fails validation.

### Reply to the original email

This notification emails an address over the shared system SMTP settings, then replies to that email once the
deployment recovers.

```yaml title="recovery-system-smtp.yaml" file=<rootDir>/modules/mission-control/fixtures/notifications/recovery-system-smtp.yaml {14-16}
```

This example:

1. Uses `to.email` so delivery goes through the system SMTP Connection or the SMTP environment settings.
2. Uses `onResolved.enabled` on its own, because the `slack` block does not apply to email delivery.
3. Achieves a recovery mail that carries the original `Re:` subject and the `In-Reply-To` and `References` headers, so
   mail clients thread it with the alert.

Mission Control records the recipients, sender and subject at the time of the original send. Reserve the `Message-ID`,
`In-Reply-To`, `References`, `From`, `To` and `Subject` headers for Mission Control — overriding them through
`to.properties` breaks threading.

### Write your own recovery message

This notification delivers through a named SMTP Connection and replaces the default recovery body with a template.

```yaml title="recovery-named-smtp.yaml" file=<rootDir>/modules/mission-control/fixtures/notifications/recovery-named-smtp.yaml {39-42}
```

This example:

1. Uses `to.connection` to send through the `recovery-smtp` Connection instead of the system SMTP settings.
2. Uses `onResolved.template` to replace the default body.
3. Achieves a one-line recovery mail naming the resource, the recovery time and the length of the outage.

Without `template`, the body names the resource and reports the recovery time and the outage duration.

## Permissions

A notification that delivers through a named Connection needs read permission on that Connection during recovery, not
only during the original send. Credentials are read again for every recovery attempt, so revoking the permission or
deleting the Connection stops the recovery update. A missing named Connection never falls back to system SMTP.

Delivery over system SMTP — `to.email`, `to.person`, or the `system` SMTP Connection — uses the shared application
mail settings and needs no per-notification grant.

## Retries

Mission Control reconciles pending recovery updates every 15 seconds in the `NotificationRecoveries` job, and runs a
safety sweep every 5 minutes in `NotificationRecoverySweep`.

A failed recovery retries with exponential backoff — 2, 4, 8, 16, 32, 64 and 128 seconds. Set
`notification.recovery.max-retries` to change the budget; the default is 7 retries after the first attempt. Set it to
`0` to disable retries.

Once the budget runs out the delivery is marked `recovery-exhausted` and is no longer retried on its own. Raising
`notification.recovery.max-retries` does not restart an exhausted delivery. Read
`job_history.details.errors` for the `NotificationRecoveries` job to find the cause, which is usually a revoked
permission, a deleted Connection or a deleted notification.

:::warning Delivery is not transactional
A transport call that times out can leave the outcome of a recovery update uncertain. Check the Slack channel or
mailbox before retrying a delivery by hand.
:::

## Retention

Mission Control prunes resolved recovery state every hour. All of the properties below take the prefix
`notification.recovery.`, and every duration accepts Go syntax along with the `d`, `w` and `y` units, so `720h`, `30d`
and `4w2d` are the same value.

| Property | Default | Description |
| --- | --- | --- |
| `max-retries` | `7` | Retries after the first recovery attempt |
| `wake.batch-size` | `20` | Deliveries scheduled per resource when it turns healthy |
| `sweep.interval` | `5m` | How often the safety sweep runs |
| `sweep.batch-size` | `100` | Maximum resources per sweep |
| `sweep.budget` | `5s` | Sweep timeout |
| `retention.interval` | `1h` | How often cleanup runs |
| `retention.batch-size` | `500` | Maximum deletes per category per run |
| `retention.budget` | `5s` | Cleanup transaction timeout |
| `retention.resolved` | `720h` | Age at which resolved deliveries are deleted |
| `retention.exhausted` | `2160h` | Age at which exhausted deliveries are deleted |
| `retention.episodes` | `720h` | Age at which ended health episodes are deleted |
| `retention.deleted-states` | `720h` | Grace period before a deleted resource's health state is pruned. Values under `720h` are raised to `720h` |

Set a retention duration to `0` to keep that category forever. Cleanup skips active, unsent and ambiguous deliveries,
so a delivery is only ever aged out after it is resolved or exhausted. Recovery state holds destination addresses,
subjects and conversation IDs, so include it in your backup and privacy procedures.

Mission Control reads `sweep.interval` and `retention.interval` when jobs are registered. Restart Mission Control to
pick up a new interval; the other properties are read on each run.
